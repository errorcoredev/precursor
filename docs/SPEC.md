# Runtime evidence engine specification

Status: implemented and verified; actual command results are recorded in the implementation plan and benchmark report. This repository contains no production capture schema. The Errorcore adapter below is illustrative.

## 1. Scope and invariants

Repository delivery separates public library/demo files from local verification assets. `tests/`, `benchmarks/`, their local configuration, `localTests/`, capture storage and generated output are ignored and removed from Git tracking while retained on disk. The public build compiles only `src/` and `examples/`; the runnable demo uses a synthetic fixture under `examples/` so a fresh checkout remains runnable. Local tests/benchmarks use a separate development TypeScript configuration. Historical benchmark measurements remain documented, while their raw artifacts are local.

Node.js 24, strict TypeScript, ESM, in-process library. Preserve received binary JSON bytes exactly, with no additional redaction. Compile deterministically into immutable source evidence, a sparse navigable index and source-supported graph. No inference, root-cause determination, authentication service or distributed infrastructure. A debugging session starts with `getOverview`.

## 2. Architecture

`compiler` connects binary input, UTF-8 validation, a strict JSON verifier, unpacked stream-json tokens, a structural writer, and an adapter session. `storage` provides local staging/publication and SQLite. `indexing` owns the versioned binary structural representation. `adapters` owns source semantics. `graph` resolves references in SQLite. `retrieval` implements bounded projections and authenticated continuations. `src/index.ts` exports the four operations and a configured engine factory.

## 3. Data model and provenance

Each capture has a random UUID. A node ID is `<capture UUID>:<structural byte offset>`. The offset addresses a validated structural record, never a purported original-file location. `PayloadReference` names the structural format/version and record offset. Nodes include type, parent, member ordinal, decoded key (when applicable), child count, availability and provenance. Paths use RFC 6901 escaping. Duplicate keys have distinct record offsets and member ordinals; pointer uniqueness must not be assumed. Pointer ambiguity is explicitly reported conservatively for object-member paths until uniqueness is established.

Provenance identifies capture, node and origin: `direct_observation`, `upstream_metadata`, or `derived_structure`. Nodes have separate `provenance` and `structureProvenance`; availability and graph records carry upstream provenance. Large keys/paths/metadata are represented by bounded previews, original lengths and resolvable node references. Structural previews are 128 units; semantic previews are 256 units. String storage uses UTF-16LE to preserve lone surrogates. Numbers retain their exact ASCII lexemes; JavaScript numeric conversion is never required. JSON null is observed.

## 4. Public contracts

The file-runner command `npm run capture -- <file.json> [--adapter=<adapter ID>]` accepts a caller-selected input file and defaults to `generic-json`. It streams that file into `.errorcore-evidence` relative to the working directory, calls `getOverview` first, then prints one root inspection page and one evidence result (the first returned child, or the root for primitives/empty containers). Each API response retains its normal bounds and continuation metadata. The input file is never modified. CLI stdout is intentional evidence output; failures print fixed codes without raw source excerpts. The illustrative graph adapter requires explicit selection with `--adapter=errorcore-example-v1`.

`createEvidenceEngine({storage, adapters?, limits?})` exposes `compileRuntimeState(input, options?)`, `getOverview(captureId, options?)`, `inspectNode(nodeId, options?)`, and `getEvidence(nodeId, options?)`. Top-level operations lazily use `.errorcore-evidence` in the current directory. Storage is a trusted configured dependency; callers cannot pass paths to retrieval.

Compile options select an adapter, optional abort signal and optional input byte limit (`maxBytes`). The manifest includes integrity hashes and sizes for source, structural file and semantic database, counts, root evidence ID, completeness, version and ingestion metrics. The manifest's output ceiling is the engine's `outputBytes`. Overview returns independent pages of failure records, operations and relationships, a root evidence reference, explicit availability-wrapper counts and graph completeness. Inspection returns child references and optional recursive expansion with a shared entry budget. Evidence returns scalar values, exact numeric-lexeme slices, UTF-16 string slices, ordered collection entries, captured-value references, or unavailable metadata. Collection entries carry references rather than recursively materializing arbitrary objects. `part: 'key' | 'pointer'` retrieves full key/path text in bounded slices. All public results fit their serialized-byte budget or fail with an explicit resource-limit error when even a minimal record cannot fit. The exported TypeScript interfaces in `src/types/index.ts` are the concrete wire contracts.

## 5. Limits and errors

Defaults: output 65,536 bytes, hard maximum 1,048,576; minimum output budget 4,096; overview 25 operations, 50 relationships and 10 failures; inspection/evidence collection page 50 entries; inspection depth 1, maximum 4; scalar slice 4,096 UTF-16 units. Per-page entry limits have a maximum of 1,000; scalar slice maximum is 262,144 units. Ingestion defaults: nesting 256, key 65,536 decoded UTF-16 bytes, pointer 262,144 UTF-16 bytes. Hard ceilings are 1,024 levels, 1,048,576 key bytes and 2,097,152 pointer bytes. Limits, identifiers, cursors, options and adapter IDs are validated; identifiers are checked before resolving store paths. `EvidenceError.code` is one of `INVALID_ARGUMENT`, `INVALID_CURSOR`, `CAPTURE_NOT_FOUND`, `NODE_NOT_FOUND`, `INVALID_INPUT`, `INVALID_JSON`, `RESOURCE_LIMIT`, `ABORTED`, `STORAGE_ERROR`, `INTEGRITY_ERROR`, or `UNSUPPORTED_VERSION`. Error messages and metrics exclude raw evidence and parser diagnostic excerpts.

## 6. Streaming and validation

Only Buffer/Uint8Array chunks are accepted. Reject streams configured with a string encoding. Split oversized input chunks into at most 64 KiB processing segments (caller-owned buffers are outside engine memory guarantees). A fatal streaming TextDecoder validates UTF-8; stream-json 3.8.0 `verifier.asStream` validates grammar independently of `parser.asStream`. Packing is disabled for keys, strings and numbers. Input is written to original storage and hashed before downstream consumption, with backpressure. Adapter state and open-container state are bounded by depth and metadata limits. Source JSON is never parsed as a whole object. Leading UTF-8 BOMs and non-JSON whitespace are rejected. Validation tests include bytewise splits, malformed UTF-8 and invalid escapes/numbers/trailing delimiters.

## 7. Structural format and indexing

A file header identifies format/version. Each value has a fixed-size record header, a UTF-16LE key, and either scalar data or nested records. Header fields include type, parent offset, member ordinal, next-subtree offset, child count, key length and scalar length. Writers use a bounded buffer and patch container/scalar lengths only in staging. Readers validate magic, record boundaries, parent chains and lengths. Container links permit skipping arbitrarily large descendants. A caller-supplied offset is accepted only when its parent/member lineage is verified, or it is present in the trusted sparse cache.

SQLite initially indexes the root, the first bounded page of root children and semantic references. Lazy inspection stores encountered nodes and immediate-child checkpoints in a separate mutable cache database. No per-array-element SQLite row is required at compile time. First uncached random access can scan siblings; cursor continuation carries the next validated ordinal/record location. Strings are seekable by UTF-16 code-unit offset and may split surrogate pairs; concatenating slices reconstructs the original string. Numeric slices concatenate to the exact original lexeme.

## 8. Storage and publication

`EvidenceStorage` isolates stage creation, commit, discard and open from compiler/retrieval. Local storage uses `staging/<UUID>` and `captures/<UUID>`, with `source.json`, `structure.bin`, `evidence.sqlite`, `manifest.json`; caches live outside committed directories. Stage files are flushed, the staging SQLite transaction committed and handles closed before same-volume atomic directory rename. SQLite's configured page cache is 2 MiB and temporary graph tables are disk-backed. Public readers only open committed directories. A crash can leave an unreachable staging directory. No automatic deletion of unrelated data. Committed evidence is immutable through the API; filesystem owners remain trusted. Rename gives process-crash atomic visibility, not a portable guarantee against hardware failure/power loss on every filesystem. `LocalEvidenceStorage.verify(captureId)` checks all three data hashes; retrieval validates sizes/format and structural bounds without rehashing a huge file on every call. Cancellation racing the atomic publication point cannot revoke a completed commit. The current storage interface materializes files; remote blobs and Postgres require further backend implementation, as described in ARCHITECTURE.md.

## 9. Adapter contract and synthetic schema

Adapters create an isolated streaming session for each compile. Sessions receive bounded start/end structural events, scalar previews with exact lengths and references, and emit semantic rows through a sink. They must not accumulate complete runtime objects or graph-sized state. Large metadata stays referenceable even when its preview is incomplete. Generic JSON emits no semantic graph.

The `errorcore-example-v1` adapter requires root `$schema: "errorcore.example/v1"`. Root arrays `operations`, `relationships`, and `failures` contain explicit records. Operations have string `id`, optional string `label`, string `correlationId`, `snapshot`, and `status`; status `failed` records a failure. Relationships have string `from`, string `to` and `type` from `parent`, `call`, `await`, `trigger`, `sequence`, `dependency`. Failure records have string `operationId`, optional string `message` and `primary: true`. Missing/non-string/over-limit source IDs remain unresolved, without coercion. Availability objects anywhere use `$availability` with status `observed`, `redacted`, `truncated`, `not_captured`, `unknown`, or `unresolved`, optional string `reason`, optional string `$runtimeType`, and `value` for captured content. Only the selected adapter interprets these fields. Explicit unavailable wrappers return metadata; source members remain preserved and structurally navigable as direct source observations. Truncated/observed wrappers point to their captured `value`; a missing value is explicitly unresolved. Truncation follows the value reference and its descendants through `sourceComplete: false`. Runtime type encodings are reported as upstream metadata, never reconstructed into non-JSON values. Duplicate reserved semantic fields are rejected as an ambiguous illustrative-schema record. Duplicate ordinary runtime keys remain supported.

## 10. Graph rules and overview

Operations are identified by their source record, preventing source-ID collision. Original IDs/correlation fields retain previews and references. Indexed exact source IDs up to 1,024 code units resolve edges; over-limit IDs remain explicitly unresolved. Multiple operations with the same source ID remain ambiguous. Every edge retains source type and source record. No edges are inferred from array order, labels or elapsed time. Every recorded failure persists; primary is true only for an explicit upstream primary flag. Generic graph completeness is unavailable. Synthetic graph completeness is partial (v1 establishes no stronger completeness claim). Count missing/ambiguous/unresolved relationship endpoints and retain those edges. Projection order: failure operations, known explicit parent/call ancestors, immediate connections, then source order; relationship priority follows the best endpoint priority. Focused projections prioritize the supplied operation and incident relationships. Independent cursors exhaust failures, operations and relationships, with exact remaining counts. Full graph storage is disk-backed. Default pagination uses indexed priority/source order with SQL OFFSET; focused queries can scan/sort persisted records. This is bounded in memory, not a constant-latency guarantee.

## 11. Response budgets and cursors

Measure final responses using UTF-8 JSON serialization. Add entries only while the complete envelope (including continuation) fits. Scalar slices are reduced until they fit. Preview fields carry lengths and completeness labels. Cursors contain format version, capture/node binding, query shape and position, signed with HMAC-SHA256 using a persisted per-store random key. Bad signatures, cross-node/query use, unsupported cursor versions, invalid positions and malformed encodings fail with `INVALID_CURSOR`. Query shape includes inspection depth, evidence part and overview focus, but excludes page size/output budget. Overview sections return `endCursor` even when exhausted; pass all three end cursors to continue the combined projection without restarting exhausted sections. `nextCursor` is absent when no records remain. Source incompleteness and response pagination are separate fields.

## 12. Verification and acceptance

Overview `captureNotes` explicitly scopes `captureComplete` to validation and publication of the received document. It never asserts that the source captured the complete runtime state.

Unit/integration coverage includes exact bytes/hash, all JSON types, escaped pointers, duplicate keys, Unicode/lone surrogates, huge scalar lexemes, depth/key/path limits, split UTF-8/escapes, source/file boundaries, availability variants, graph provenance/failures/ambiguity, pagination without gaps, output ceilings, tampering/traversal, cancellation/invalid streams, storage fault injection, uncommitted staging invisibility and fresh-process recovery. An executable example must compile, call overview first, inspect/expand, retrieve observed and redacted evidence, show generic graph absence and reopen in a child process. Run build, typecheck, lint, tests and example before delivery.

## 13. Benchmarks, assumptions and integration

Incremental synthetic generators feed isolated Node child processes. Actual 10 MiB and 100 MiB runs, with exact byte counts, wall time, process peak RSS, sampled heap, OS/runtime/CPU, file sizes/index overhead and cold/warm retrieval, are recorded in `benchmarks/RESULTS.md` and `benchmarks/results/*.json`. The optional 1 GiB command has not been run. The measured 100 MiB workload meets the initial targets of peak RSS below 256 MiB, warm overview below 100 ms, and cached inspection/evidence below 50 ms. Cold means a fresh process without lazy cache, not a flushed operating-system cache. Sparse indexes trade disk size and scan latency for bounded ingestion memory. Synchronous bounded SQLite/structural work can block the event loop during a chunk, and graph finalization can block longer; this is an in-process foundation. Production integration requires a real schema, adapter mapping and fixtures, without changing generic storage or parser semantics. No production-schema claims are made.
